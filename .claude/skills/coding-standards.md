# コーディング規約

このリポジトリの技術スタックと制約を前提に、具体的な方針を示す。

---

## 0. このリポジトリ固有のルール

他のプロジェクトには存在しない制約。**まずここを読むこと。**

### 実測で決まった値を、理由なく動かさない

`phase0-pusher` は「プッシャーの押し出しが物理的に成立するか」を実測で確かめた検証台で、
**結果ごと凍結してある**。`arcade` の物理設定はそこで合格した値をそのまま持ち込んでいる。

`PusherSpec` の「フィールド」節と `project.godot` の `[physics]` は、
5 分間の耐久試験に通った組み合わせそのもの。実測で判明した成立条件は 4 つある。

1. 上段後方は壁の高さまでの固定壁。庇にすると 2 層目が支えを失う
2. 投入は上段の最後方、壁のすぐ手前。中央に落とすと山に積むだけになる
3. 投入そのものが動力源。「満ちたら止める」設計にすると台も止まる
4. 横穴は盤の可動域より手前だけ。可動域の脇に開けると延々とこぼれる

**これらに触る変更は、触る前に理由を書き、触ったあとに実測し直す。**
「動いたから良い」で進めない。壊れたことが分かるのは数分後の挙動なので、
その場のスクリーンショットでは判定できない。

### スケールと重力は必ずセットで動かす

長さを k 倍したら重力も k 倍にする。剛体系は「長さ k 倍・重力 a 倍」で
時間が √(k/a) 倍にスケールするので、k だけ変えると世界がスローモーションになる。

現在は 10 倍スケール・重力 98。この対応は
`arcade/tests/core/medal/medal_spec_test.gd` の
`test_gravity_matches_the_scale` が ProjectSettings から直接見張っている。

**設計書 4.1 は「重力を変えると嘘くさくなる」と書いているが、
スケールを変える場合に限って逆。** 設計書のほうが誤っている数少ない箇所で、
`docs/arcade-sim-design.md` を読むときはここだけ読み替える。

### 払い出しを確率で作らない

盤面からの払い出しは**形状だけ**で決まる(設計書 5 章)。
「還元率が目標を下回ったから少し出す」といった補正を盤面側に入れない。
獲得量を調整したいときは `Roulette.TABLE` の重みと配当で行う。
盤面の形状と抽選の乱数は、互いに触らない。

### 乱数は必ず種を指定する

`randi()` / `randf()` のグローバル関数を使わない。
`RandomNumberGenerator` のインスタンスを持ち、種を外から渡せるようにする。

```gdscript
var _rng := RandomNumberGenerator.new()

func _init(seed_value: int = 20260816) -> void:
    _rng.seed = seed_value
```

この形になっているおかげで、抽選の並びを再現してバランス検証を回せる。
グローバル乱数を 1 箇所でも使うとそれができなくなる。

### メダルは現金に戻せない

設計書 6.1 の絶対条件。`PlayerWallet` に逆両替にあたる関数を生やさない。
`player_wallet_test.gd` の `test_wallet_has_no_way_back_to_cash` が見張っている。

## 1. TDD — 原則

**Red → Green → Refactor** に従う。

### Red(失敗するテストを書く)

- 実装より先にテストを書く
- テストを実行し、**意図どおりに失敗すること**を確認する
- 「クラスが無い」「関数が無い」で落ちるのも Red として扱う
- 実装の詳細ではなく振る舞いを書く

### Green(最小限で通す)

- 落ちているテストを通すために必要な最小限だけ書く
- 美しさ・拡張性・重複排除はここでは無視してよい
- 通ったら手を止める

### Refactor

- テストが通ったまま整理する
- テストコード自体も対象
- 終わったら全部通ることを確認する

### 厳守

- **失敗するテストなしにプロダクションコードを書かない**
- **1 サイクルで 1 つの振る舞いだけ**扱う
- **テスト実行の確認を省略しない**(Red で落ちること、Green で通ることを毎回見る)

### カバレッジについて

**カバレッジの閾値は設けていない。GDScript に使えるカバレッジ計測が無いため。**

数値で守れないぶん、レビューで見る。「この振る舞いのテストはどれか」に
答えられない変更は通さない。カバレッジ率を目的にしたテストは書かない。

### 物理に依存するものはテストしない

メダルが積み上がる、山が崩れる、押し出されて落ちるといった挙動は
ソルバの結果であって、単体テストで固定するものではない。
ここは `play.cmd -Debug -Demo` で目と計器を使って確かめる領域。

テストで守るのは、その手前にある**決定的な部分**に限る。

- 寸法どうしの関係、設定値の整合(`medal_spec_test.gd`)
- 状態遷移と境界(`roulette_test.gd`, `player_wallet_test.gd`)
- 抽選表そのものの健全性

## 2. gdUnit4 テストの書き方

### 実行

```
check.cmd                  format / lint / import / test を全部
check.cmd -Only test       テストだけ
check.cmd -Fix             gdformat をかけてから全部
```

CI と同じコマンドを `scripts/check.ps1` が呼んでいる。
検査を足すときは `.github/workflows/ci.yml` も一緒に直す。片方だけだと必ずズレる。

### ファイル構成

- テストは `arcade/tests/` 以下に、`arcade/src/` と同じ階層で置く
  - `src/core/player_wallet.gd` → `tests/core/player_wallet_test.gd`
- ファイル名は `*_test.gd` で統一する
- `phase0-pusher` にはテストを書かない(凍結した検証台のため、構文チェックのみ)

### 基本形

```gdscript
extends GdUnitTestSuite


func test_spend_fails_when_empty() -> void:
    var wallet := PlayerWallet.new()
    assert_bool(wallet.spend_medal()).is_false()
```

- `RefCounted` 派生はそのまま `new()` してよい
- `Node` 派生は `auto_free()` で包む。忘れると orphan として報告される

```gdscript
func _roulette(seed_value: int = SEED) -> Roulette:
    return auto_free(Roulette.new(seed_value))
```

### 落ちたときに原因が分かるようにする

ループの中の assert には `override_failure_message()` を付ける。
どの要素で落ちたのかが分からないと、表を直すのに時間を取られる。

```gdscript
for entry in Roulette.TABLE:
    assert_int(entry["weight"]).override_failure_message(
        "%s の重みが 0 以下。抽選から漏れる" % entry["outcome"]
    ).is_greater(0)
```

### 定数は「値」ではなく「関係」を見る

実測値は調整して構わない。壊れて困るのは値どうしの関係のほう。

```gdscript
# 悪い: 調整のたびにテストを直すことになる
assert_float(MedalSpec.FRICTION).is_equal(0.14)

# 良い: 実測メモにある帯から外れたら止める
assert_float(MedalSpec.FRICTION).is_between(0.12, 0.19)

# 良い: 積み重なりの安定を支えている関係そのもの
assert_float(MedalSpec.COLLISION_THICKNESS).is_greater(MedalSpec.VISUAL_THICKNESS)
```

### 境界を必ず洗う

- 0 枚から使おうとする / ちょうど 0 枚になった直後
- 保留が上限に達したあと、さらに足したとき
- 在庫より多く払い出そうとしたとき
- 種が同じなら並びが一致すること、違えば一致しないこと

### `_process` を直接呼んでよい

時間で進む状態機械は、`_process(delta)` を手で呼んで進める。
実時間を待たずに決定的に検証できる。

ただし 1 ティックで何が起きるかは実装しだい。
たとえば `Roulette` は「間(hold)を消化するティック」でそのまま `return` するので、
回り始めるのは次のティックになる。**推測せず、落ちたら実装を読む。**

## 3. GDScript の書き方

### 書式

`gdformat` / `gdlint` に従う。手で整えない。

`.gdlintrc` で `class-definitions-order` を切ってある。
Spec 系は定数を話題ごとに固め、それぞれに実測の根拠を書いてあるので、
機械的な並び順を強制すると根拠と値が離れてしまう。並びより根拠を優先する。

### 型を書く

- 変数は `:=` で推論させるか、型を明示する
- 関数の引数と戻り値には必ず型を書く。戻り値が無いなら `-> void`
- `Array[int]` のように要素の型も書く

### 命名

- ファイル・関数・変数は `snake_case`、クラスと定数は `PascalCase` / `UPPER_SNAKE`
- 外に出さないものは `_` を先頭に付ける
- 単位が要るものは名前に入れる(`SPIN_SEC`, `DIAMETER_MM`)

### 定数に根拠を書く

実測で決めた値には、**何を見てその値にしたか**をそばに書く。
値だけ残っていると、次に触る人が動かしてよいのか判断できない。

```gdscript
## 0.19 では山が盛りすぎ、0.12 では平らになるが実物の下限(0.15)を割る。
## 使い込まれて磨れた真鍮メダルの下限あたりに置いてある。
const FRICTION := 0.14
```

### マジックナンバーを散らさない

寸法と時間は Spec クラス(`MedalSpec`, `PusherSpec`)に集める。
呼び出し側に数値を直接書かない。

### signal

- 状態が変わったことは signal で外に出す。呼び出し側を直接叩きに行かない
- **変化が無いときは出さない。** 上限で頭打ちになったとき、
  0 枚のとき、無視する引数のときは黙る。テストでもそれを確かめる

### class_name を足したら再インポート

グローバルクラスの登録は起動時に更新されないことがある。
`play.cmd -Import` を 1 度通す。CI は毎回 `--headless --import` を通している。

## 4. Git の進め方

`CLAUDE.md` に書いてある。要点だけ。

- `main` へ直接 push しない。短命のブランチと PR を通す
- 1 つの PR は 1 つの論理的な変更
- Conventional Commits の prefix + 日本語の本文
- **整形だけのコミットは `style:` で単独にする。** 実装の差分と混ぜない

---

## 5. やらないこと

- テストなしのプロダクションコード
- 「あとでテストを書く」
- 実測で決まった物理値を、理由を書かずに動かす
- 盤面の払い出しに確率の補正を入れる
- グローバルの `randi()` / `randf()`
- カバレッジ率を目的にしたテスト
- ソルバの結果(積み上がり・崩れ)を単体テストで固定しようとすること
- 逆両替にあたる関数
